Multi-level Questions App Guide

What changed in the app API for the eight question nesting cases, and what the app has to change to draw, save and submit them.

Nothing breaks for the current app. Every field the app reads today is still sent with the same meaning. The API only adds fields and fills in the levels it used to leave out. Cases 1 to 4 keep working unchanged; cases 5 to 8 need the app changes below.

The eight cases

An activity can nest questions in these shapes only (max 2 Multi Response levels, 2 conditional levels, 4 levels in total). Full rules: docs/Question Nesting Rules.html.

#StructureLevels
1Yes / No = Yes → any question2
2Dropdown = option → any question2
3Multi Response → sub-questions2
4Multi Response → Yes / No or Dropdown → any question3
5Yes / No or Dropdown → Yes / No or Dropdown → any question3
6Multi Response → Yes / No or Dropdown → Yes / No or Dropdown → any question4
7Multi Response → Multi Response → sub-questions3
8Multi Response → Multi Response → Yes / No or Dropdown → any question4

1. getAllQuestion: the question tree

GET /api/getAllQuestion?row_id=…&activity_id=… returns the same data array as before: root questions only, each child nested inside its parent. Two places hold children:

  • sub_questions[].child_question: members of a Multi Response group. They are always shown. A member can itself be a Multi Response (a child group) with its own sub_questions.
  • conditional_questions[]: questions shown only when this question's answer matches their trigger_value. Every question now has this array (empty when it has none), at every level.

This is the tree the API sends for a test activity that uses all eight cases. It is the same structure and the same codes the auditor web form shows:

New fields on every question, at every level

FieldMeaning
question_codeCode to show next to the question, the same as on the web form: Q003, a group member Q003b, a child group member Q003b1, a conditional question its parent's code plus a letter (Q003b1a). Before, only roots and first-level members had one.
level1 for a root question, up to 4. Use it for indentation.
parent_context_idThe context this question's answer is saved under: null for a root question, the group's id for a group member, the parent's id for a conditional question. Send it back when saving.
answer_keyThe same thing as one string: "2634" or "2643_pctx_2642". Use it as the key of the app's local answer state and as the field name in answerSubmit.
conditional_questionsNow on every question, recursively. Each item also has trigger_value and parent_question_name.
on_clickNow on every question: true when one of its conditional questions shows on any answer.

Smaller corrections in the same response

  • A group member that is conditional on a sibling member is no longer sent twice. It appears only inside that sibling's conditional_questions. Its code is the same as on the web form, so codes after it in that group can move by one letter.
  • A question that is both a member of a group and "conditional" on that same group is sent only as a member.
  • A group link to a deleted question (empty child_question) is no longer sent.
  • Members of a child group now have parent_question_id set to the child group, as first-level members already had.

2. Drawing the form

Draw the tree with one recursive function, so every level works the same way and no level is skipped:

// answers: { [answer_key]: value }   (local state, keyed by answer_key)
function renderQuestion(q) {
  if (q.question_type === 'Multi Response') {
    drawGroupCard(q);                          // heading only: no input, never answered
    q.sub_questions.forEach(link => renderQuestion(link.child_question));
  } else {
    drawQuestion(q);                           // code badge + text + input by question_type
  }
  q.conditional_questions
    .filter(c => isTriggered(c, answers[q.answer_key]))
    .forEach(c => renderQuestion(c));          // directly under the parent
}

function isTriggered(c, parentValue) {
  const v = String(parentValue ?? '').trim();
  const t = String(c.trigger_value ?? '').trim();
  if (t === '' || t === '__non_empty__') return v !== '';   // "any answer"
  return v.toLowerCase() === t.toLowerCase();
}

data.forEach(renderQuestion);
  • Indent by level (about 12 to 14 px per level), and show question_code as a small badge. The web form colours levels 2, 3 and 4 blue, green and orange.
  • A child group (a Multi Response inside a Multi Response) is a card inside the parent group's card, with its own members inside it.
  • Re-evaluate on every change. When an answer changes, redraw that question's conditional questions. A hidden question hides its whole branch, because renderQuestion never reaches the questions below it.
  • Clear hidden answers. When a branch becomes hidden, clear its local answers and don't send them. The server also deletes answers of hidden branches when the activity is submitted, so a stale answer never reaches the verifier or reports.
  • Required (answer_type = 1) applies only while a question is shown. Never block Submit on a hidden question.

3. Prefilling saved answers

answer_data.original.answers[] (and each instance's answers) already carry question_id and parent_context_id. Build the same key the questions use:

const keyOf = a => a.parent_context_id ? `${a.question_id}_pctx_${a.parent_context_id}` : `${a.question_id}`;
const saved = Object.fromEntries(answerList.map(a => [keyOf(a), a.user_answer]));

// Answers saved by older app versions have no context: fall back to the plain question id
const prefill = q => saved[q.answer_key] ?? saved[String(q.id)];

4. Saving an answer

POST /api/saveAnswer (form-data), one answer per call, the same as today. The clearest way is the question id plus the new parent_context_id field:

row_id=408568
activity_id=140
activity_sequence=0
latitude=19.0760            (required on the first answer of the instance)
longitude=72.8777
question_id=2643
parent_context_id=2642      (the question's parent_context_id; leave it out for a root question)
value=…                     (or the file in "file" for Image / Audio / Video / File Upload)
  • The existing key formats still work: {answer_key}=value (for example 2643_pctx_2642=…), and the reversed {group}_pctx_{question} that some app versions send.
  • A parent_context_id that is neither the question's group nor its parent is refused with 422 and a message naming both ids.
  • If the same question was saved earlier without a context (older app versions did this for conditional questions), the server now updates that answer and gives it the context. It doesn't create a second copy.
  • The response's data.parent_context_id shows the context it was saved under.

5. Submitting

No change in how the app calls Submit: saveAnswer without a question_id, or POST /api/finalizeAnswers. What the server now does on submit:

  1. Deletes the answers of every branch that is hidden by the current answers, at every level (the web form already did this).
  2. Checks required questions at every level: root questions, group members at any depth, and conditional questions only while their whole parent chain is shown.
  3. Marks the instance's answers as submitted (status 1), as before.

A missing required answer returns 422 with the same missing list as before:

{ "status": 422, "message": "Please answer all required (*) questions.",
  "missing": [ { "question_id": 2643, "question": "Fridge photo (not clean)" } ] }

Behaviour change: finalizeAnswers used to skip conditional questions entirely. It now requires a shown conditional question that is marked required, exactly like saveAnswer's submit and the web form.

6. Bulk answerSubmit

If the app uses POST /api/answerSubmit, send each answer under its answer_key (for example 2637_pctx_2636=Milk) and pre-uploaded images as multi_images_{answer_key}[]. Fixed on the server:

  • Validation and saving used to read _pctx_ keys in opposite orders, so group answers could be saved under the group's id. Both now read the key the same way, and the reversed order is detected.
  • An answer is updated per question and context. Before, one value overwrote the question in every context.
  • Required conditional questions are judged on the saved answers plus the values in this request. Before, a parent answered in the same request didn't count. Images sent as multi_images_… count as answered.
  • Hidden-branch answers are removed after saving.

Checklist for the app

  • Render questions with one recursive function over sub_questions and conditional_questions (no fixed number of levels).
  • Key local answers by answer_key; prefill with the fallback to the plain question id.
  • Show question_code and indent by level; draw a child group as a card inside its group.
  • Show or hide conditional questions with isTriggered, re-run on every answer change, and clear answers of hidden branches.
  • Send parent_context_id (or use answer_key as the field name) on every saveAnswer call.
  • Treat required only for shown questions, and show the server's missing list on a 422 from Submit.
  • Test all eight cases: answer, change a parent answer to hide a branch, reopen the activity, submit.

Server files changed

  • app/Http/Controllers/API/TaskController.php: getAllQuestion, saveAnswer, submit mode, finalizeAnswers, answerSubmit.
  • app/Services/ConditionalAnswers.php (new): shared rules for which conditional questions are shown, hidden-branch cleanup and required questions.
  • app/Http/Controllers/Masters/TaskHandlerController.php: the web form now uses the same shared rules.
