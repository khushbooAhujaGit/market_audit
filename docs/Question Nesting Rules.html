Question Nesting Rules

Which multi-level question structures an activity may use, why exactly these eight cases are supported, and what unlimited nesting would break later.

Applies to: activity questions (admin), auditor web form, app API, verifier screen, reportsDate: 29 Oct 2026
Decision

Activities may nest questions only in the eight shapes below. Every structure is built from two moves (a Multi Response group and its sub-questions, or a Yes / No or Dropdown answer and its conditional questions), within three limits:

max 2 Multi Response levels max 2 conditional levels max 4 levels overall a child group has one parent

How a question can go one level down

The database can store any depth. What decides the shapes is what each question type can do.

Question typeHas an answer?Can open questions below it?Can sit inside a Multi Response?Can be shown by an answer?
Multi ResponseNo, it is a headingYes: its sub-questions, always visibleYes, as a child groupNo
Yes / No DropdownYes, from a fixed listYes: conditional questions for a chosen answerYesYes
Free Text · Image · Date · Date & Time · Multi select · File Upload · Video · Audio · Location · Barcode / QR Code / RFID · SubjectiveYesNo (only the “any answer” trigger)YesYes

Only Yes / No and Dropdown have fixed answers that can be matched exactly. Free text, a photo or a date has no fixed value to compare, so those types end a branch. A Multi Response has no answer of its own, so it can neither open conditional questions nor be shown by one.

Why exactly these eight

They are every combination of the two moves

A group opens sub-questions; a choice question opens conditional questions. Combining those two moves within the limits gives these eight shapes and no others.

They cover real audits

Across all 1,378 existing questions, the deepest structure in use is 3 levels. Four levels leaves room to grow without new risk.

Every part can support them

The web form, app, verifier screen and reports can each handle these shapes. Anything deeper would be saved by one part and lost by another.

They stay readable

Question codes stay short (Q004d2a), the form fits a phone screen, and report columns stay understandable.

What unlimited nesting would cause

Unlimited nesting is technically possible: the database can hold it. These are the problems it would create later.

  1. Answers that the app, verifier or reports never see

    Each part walks a fixed number of levels. A question deeper than a part supports is answered and saved in one place, but never reaches the app, never appears for the verifier, and gets no column in Excel.

    Example today: a second-level conditional question has no column in the Report Dump.

  2. Changing one answer deletes a large branch

    When a top answer changes, every answer under the branch it hides is removed on Save, so reports stay correct. With deep trees one tap can wipe many answers, photos included.

  3. Auditors miss questions

    Deeper branches hide more questions behind earlier answers. Auditors cannot see what is coming, and one wrong early answer silently skips a whole section.

  4. The form stops fitting a phone

    Every level is indented. On a 360 to 400 px screen, five or six levels leave little width for the question and the answer field.

  5. Testing grows exponentially

    With three answers per question, the number of paths is 3 to the power of the depth: 3⁴ = 81 at four levels, 3⁶ = 729 at six. Each path has to work on the web, the app, the verifier screen and the reports.

  6. Reports become unreadable

    Every level adds columns that are empty for most outlets, and the relation text (Outlet status = Open → Asset available? = Yes → Condition = Damaged → …) becomes too long to use.

  7. Question codes lose their meaning

    Codes grow with depth (Q004d2aab…) and stop helping auditors, verifiers and support staff talk about a question.

  8. Loops can be created by mistake

    Without a limit, an admin can make A depend on B and B depend on A. The form would then never settle. A depth limit, with a loop check when questions are saved, prevents this.

  9. Shared groups overwrite each other’s answers

    Answers are keyed by the nearest parent. A child group reused under two parents would share one set of answers. Deep, unlimited trees make this much harder to notice.

  10. Slower forms, app and reports

    Each level adds database queries when the form loads, more data in the app’s question API, and more lookups when a report runs over thousands of outlets.

  11. Every new shape needs app work

    The app developer has to build each structure the API sends. A fixed set of shapes is a contract the app can rely on; unlimited nesting is not.

Recommendation

Keep the eight cases and the limits above. Enforce them when questions are created, so an activity can never hold a structure that some part of the system cannot show, save, verify or report. Once the app API, verifier screen and reports handle every level, the limit becomes a single setting that can be raised if a real audit ever needs it.
